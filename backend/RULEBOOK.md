# Backend Rulebook (внутренний стандарт)

## 1. Назначение правил

Этот документ обязателен для всех backend-задач в репозитории.
Цель: сохранять архитектурную целостность, долгосрочную сопровождаемость и надежность в продакшене.

Приоритеты:
1. Корректная архитектура и границы слоев.
2. Полное и поддерживаемое тестирование реализованного поведения.
3. Надежность и безопасность.
4. Скорость реализации.

Если скорость конфликтует с архитектурой или качеством тестов, всегда выбирается архитектура и тесты.

## 2. Ключевые архитектурные принципы backend

1. Архитектура первична.
   - Любое изменение начинается с правильного размещения кода по слоям.
   - Временные архитектурные обходы запрещены.

2. Бизнес-логика только в domain/application.
   - Бизнес-правила запрещено размещать в контроллерах, security-конфигурации/фильтрах, репозиториях и framework glue code.

3. Фреймворк на периферии.
   - Spring Boot - инструмент реализации, а не архитектурный центр.
   - Domain/Application не зависят от транспортных и инфраструктурных деталей.

4. Явные границы и контракты.
   - Межслойные вызовы только через явные контракты (команды, запросы, DTO, порты).
   - Скрытая связанность через framework-объекты и persistence-модели запрещена.

5. Сопровождаемость важнее быстрых хаков.
   - Решения проектируются под безопасные будущие изменения: низкая связанность, понятная ответственность, локальный эффект изменений.

## 3. Правила слоев и зависимостей

Слои:
- Domain
- Application (use-case слой)
- Infrastructure
- Web/Transport
- Security
- Configuration

Разрешенные зависимости:
- Web -> Application
- Security -> Application (и доменные policy-абстракции при необходимости)
- Application -> Domain
- Infrastructure -> Application/Domain (реализация портов)
- Configuration -> все слои (только wiring)

Запрещенные зависимости:
- Domain -> любой внешний слой
- Application -> Web/Transport
- Application -> concrete infrastructure/framework internals
- Web -> Domain или Repository напрямую
- Security -> Repository напрямую (кроме строго оформленного инфраструктурного адаптера по контракту)
- Любые циклические зависимости между модулями/пакетами

Правило enforcement:
- Если реализация требует обратной зависимости, работа останавливается до введения корректного порта/границы.

## 4. Правила для domain, application, infrastructure, controllers, security, configuration

### Domain
- Должен содержать инварианты, бизнес-решения и предметное поведение.
- Не должен зависеть от Spring, HTTP, security filters, persistence APIs.
- Не должен выполнять I/O, доступ к БД/сети и прямой доступ ко времени.

### Application (Use-Case)
- Должен оркестрировать use-case-сценарии, транзакции и workflow.
- Должен использовать порты/абстракции для persistence и внешних систем.
- Не должен содержать HTTP-детали и SQL/JPA-детали.
- Не должен быть "тонкой прокладкой" без сценарной логики.

### Infrastructure
- Должен реализовывать порты и изолировать framework/external details.
- Не должен содержать бизнес-решения и предметные правила.
- Не должен протекать наружу инфраструктурными моделями вместо доменных контрактов.

### Controllers / Transport
- Должны делать только: маппинг запроса, валидацию входного контракта, вызов use-case, маппинг ответа.
- Не должны содержать бизнес-ветвления, транзакционные решения и предметные вычисления.
- Не должны обращаться к репозиториям напрямую.

### Security
- Должен централизованно обеспечивать аутентификацию/авторизацию.
- Должен иметь явное поведение allow/deny.
- Не должен содержать доменные бизнес-вычисления в фильтрах/конфиге.
- Не должен ослабляться "временно" ради скорости.

### Configuration
- Должен содержать только wiring, свойства и инфраструктурную конфигурацию.
- Не должен содержать бизнес-логику и скрытые runtime-ветки предметной области.

## 5. Стратегия тестирования и обязательные правила тестов

Общие обязательные правила:
- Тесты обязательны для каждого backend-изменения.
- Покрытие означает покрытие поведения, а не метрики строк.
- Тесты должны быть детерминированными, читаемыми и устойчивыми к рефакторингу.
- Поверхностные тесты "ради покрытия" запрещены.

Обязательные типы тестов и их ответственность:

1. Unit tests (Domain/Application)
- Проверяют бизнес-правила, ветви решений, инварианты и edge cases.
- Моки допустимы только для внешних зависимостей/портов.
- Мокать бизнес-логику, которую тестируют, запрещено.

2. Integration tests (Application + Infrastructure)
- Проверяют реальную совместную работу use-case слоя и инфраструктурных адаптеров.
- Покрывают транзакции, маппинг и persistence side effects.
- Проверки persistence-поведения нельзя заменять моками репозиториев.

3. Web/API tests
- Проверяют HTTP-контракт: статус-коды, схемы payload, ошибки валидации, сериализацию/десериализацию.
- Обязательны для каждого нового/измененного endpoint.

4. Repository/Infrastructure tests
- Проверяют поведение запросов, корректность маппинга, ограничения и ошибки инфраструктуры.
- При значимом persistence-поведении используется реалистичная среда (тестовая БД/контейнер).

5. Security/Authentication tests
- Обязательны для любого security-чувствительного изменения.
- Обязаны покрывать allow + deny, невалидные токены/креды и границы привилегий.

6. End-to-End / Full-flow tests (где необходимо)
- Обязательны, если изменение затрагивает несколько слоев или критичный бизнес-поток.
- Должны защищать от межслойных регрессий.

Минимальные сценарии покрытия для измененного поведения:
- happy path
- negative path
- edge cases
- validation failures
- error-path handling
- security-sensitive flows
- persistence behavior
- serialization/deserialization (когда применимо)
- regression case для исправленного дефекта

## 6. Definition of Done для любой backend-задачи

Backend-задача завершена только если одновременно выполнено все:

1. Архитектурные границы соблюдены, запрещенных зависимостей нет.
2. Бизнес-логика размещена корректно (только domain/application).
3. Все релевантные типы тестов добавлены/обновлены по масштабу изменений.
4. Тесты покрывают поведение, ветки решений, error-path и регрессии.
5. Изменения API-контрактов протестированы.
6. Security-поведение протестировано для релевантных сценариев.
7. Нет временных хаков, TODO-обходов и скрытого техдолга.
8. Код сопровождаем, ответственность компонентов ясна.
9. Весь релевантный тестовый набор стабильно проходит локально.

## 7. Антипаттерны / запрещенные практики

- Бизнес-логика в controller/repository/security config/filter/configuration class.
- Прямой вызов repository из controller/security в обход use-case слоя.
- Выставление persistence entities как публичного API-контракта.
- Нарушение слоев ради ускорения.
- Тестирование только happy path.
- Подмена критичных инфраструктурных проверок моками.
- Нестабильные тесты (время/random/внешние зависимости без контроля).
- Проверка приватных деталей реализации вместо наблюдаемого поведения.
- Изменение security-правил без deny/allow тестов.
- Завершение задачи при падающих тестах или непокрытой критичной логике.

## 8. Self-review checklist перед завершением задачи

Перед завершением backend-задачи агент обязан подтвердить каждый пункт:

1. Каждый новый/измененный класс расположен в корректном слое.
2. Не добавлено ни одного запрещенного направления зависимостей.
3. Бизнес-логика остается только в domain/application.
4. Контроллеры тонкие и transport-only.
5. Infrastructure остается adapter-only, без бизнес-решений.
6. Security-чувствительные изменения имеют allow/deny тесты.
7. Unit-тесты покрывают правила и ветви в domain/application.
8. Integration/repository тесты покрывают измененное persistence/adapter поведение.
9. Web/API тесты покрывают измененные контракты и валидацию.
10. Покрыты negative, edge, error и regression сценарии.
11. Тесты детерминированные и поддерживаемые.
12. В финальном коде нет временных обходов.
13. Итог оптимизирован под долгосрочное качество, а не под скорость написания.
